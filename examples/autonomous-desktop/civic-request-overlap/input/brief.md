# D03 · 市民复合诉求与联合办理

全部数据为原创合成数据，不代表真实组织。

## 负责人要完成的判断

街区协调会要判断哪些诉求适合联合办理，避免同一请求按多个标签重复派队。请同时看独立请求规模、标签交集、已投入工时、紧急未结和等待时长。不能用标签出现次数替代请求数，也不能只按体量决定优先级。必须能切换“包含任一所选标签”“包含全部所选标签”“标签恰好等于所选集合”三种问题，联动街区、具体请求和负荷。切换按请求数或紧急未结负荷排序时，保留同一组合与请求的身份，并解释已结与未结的等待口径。

## 数据定义

- 一行是一条独立request_id，不是一个居民。tags是该请求的完整标签集合，标签允许重叠。
- 任一：请求标签与选择有非空交集。全部：请求包含所有所选标签。恰好：两个标签集合完全相同。未选择标签时显示当前街区范围的全量，并明确此默认规则。
- 每个精确组合由其完整tags集合确定，集合内顺序不影响身份。
- closed_day为空表示截至snapshot_day仍未结。未结等待=snapshot_day-created_day；已结办理历时=closed_day-created_day，两者分开命名。
- urgent为原始紧急标记。紧急未结负荷按紧急且未结的请求数计算。work_minutes是截至快照已投入工时，不是预计剩余工时。
- 共享标签的工时不能按每个标签加总后冒充全量工时。跨街区不提供居民去重信息。

## 证据边界

没有联合办理干预或未来剩余工作量数据。可以建议复核联合办理对象，不能断言合并后节省多少工时，也不能用已结历时直接预测未结剩余时长。

## 桌面交付

独立决定表达方式，不向评委询问图名或预期答案。
首次提交应为完整可运行的桌面分析页面，含源数据与当前状态导出。
首屏应让负责人看见核心关系和主要取舍，细节能继续追查。
题面必要维度不可只藏在重复清单中，也不可静默省略。
支持鼠标、键盘、可见焦点、空态与恢复。
范围、选择、比较、图表、明细和行动须保持同一状态。
有价值的状态切换须能持续识别对象，支持中断、反转和运行时减少动态。
导出与打印必须对应完整稳定状态。
手机只备注基本可用，不要求专项设计。
采用EM-2桌面评分。按冻结Skill自行完成交付前质量检查，不能读取评委材料。
